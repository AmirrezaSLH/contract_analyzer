# Front End 02 · the data layer

**Status: settled 2026-08-24.** The API client, the query layer, the polling
machine, the SSE reader, and how an error becomes a screen. This is where the
front end's only real logic lives.

## 1. Types are generated, never written

`docs/openapi.json` is already a required deliverable (assignment §3.3).
`openapi-typescript` turns it into `src/api/types.gen.ts`, checked in and
regenerated by `make ui-types`.

```
make ui-types   # export openapi.json from the app, then regenerate types.gen.ts
```

The API schema stays the single source of truth for response shapes, and a
backend change that breaks the UI becomes a type error at build time rather
than a blank pane in a demo. **`types.gen.ts` is never hand-edited**, and
`src/api/` contains no `any`.

A regeneration that produces a diff in `types.gen.ts` is a signal, not noise:
read it before committing.

## 2. `api/client.ts`

One module, one place for four concerns.

```ts
const BASE = "/api";              // dev: Vite proxies it; prod: same origin

export class ApiError extends Error {
  constructor(
    readonly status: number,
    readonly code: string,        // document_not_found, no_api_key, ...
    message: string,
    readonly hint?: string,
  ) { super(message); }
}
```

* **Base URL.** Always `/api`. There is no `CA_API_URL` in the browser —
  that setting belongs to the MCP server now (`02_architecture.md` §3).
* **Trace ids.** One `X-Trace-Id` per *user-initiated action* — an upload, an
  analysis submission, a question — not per HTTP request. Minted here,
  returned to the caller, stored beside the thing it started, displayed on
  the analysis card. This is what makes the live log walkthrough of
  assignment §3.6 work: a panel member reads an id off the screen and greps
  `.run/app.jsonl` for it.
* **Errors.** Every non-2xx is parsed as `{error: {code, message, hint?}}`
  and thrown as `ApiError`. A response that is not that shape (a proxy error
  page, a 502 from nowhere) becomes `ApiError(status, "unreachable", …)` so
  the rendering layer never has to handle two shapes.
* **Upload uses `XMLHttpRequest`, everything else uses `fetch`.** `fetch` has
  no upload progress event. A 25 MB PDF over a slow link is fifteen seconds
  of nothing, and `01_ui_spec.md` §3.1 specifies a determinate bar. This is
  the only XHR in the codebase and it carries a comment saying why.

## 3. Query keys and hooks

```ts
const keys = {
  health:     ["health"] as const,
  criteria:   ["criteria"] as const,
  documents:  ["documents"] as const,
  document:   (id: string) => ["documents", id] as const,
  sections:   (id: string) => ["documents", id, "sections"] as const,
  analysis:   (id: string) => ["analyses", id] as const,
};
```

| Hook | Wraps | Notes |
|---|---|---|
| `useHealth()` | `GET /health` | Once at boot. Supplies the real upload limit and `key_present`, which gates the `no_api_key` banner |
| `useCriteria()` | `GET /criteria` | `staleTime: Infinity`. Static for the process |
| `useDocuments()` | `GET /documents` | The library and the sidebar. Invalidated by upload and delete |
| `useDocument(id)` | `GET /documents/{id}` | Sidebar meta; supplies `last_analysis` |
| `useUpload()` | `POST /documents` | Mutation; on success invalidates `documents` and returns the new id |
| `useCreateAnalysis()` | `POST /analyses` | Mutation; §4 |
| `useAnalysis(id)` | `GET /analyses/{id}` | The polling machine; §4 |
| `useDeleteDocument()` | `DELETE /documents/{id}` | Mutation; invalidates `documents`, navigates to `/library` |

**Invalidation, not refetch-everything.** An upload invalidates `documents`;
a completed analysis invalidates `documents` (the library's "last analysis"
chip is now stale) and nothing else. Blanket `queryClient.invalidateQueries()`
is a bug waiting to be a performance problem.

**`analysis_id` is derived, never stored.** It comes from
`document.last_analysis.analysis_id`, or from the mutation's response after a
submit. A local `Map<documentId, analysisId>` would be a second source of
truth for a fact the server already owns.

## 4. The polling machine

The one piece of real machinery.

```ts
export function useAnalysis(analysisId: string | null) {
  return useQuery({
    queryKey: keys.analysis(analysisId ?? ""),
    queryFn: () => api.getAnalysis(analysisId!),
    enabled: analysisId !== null,
    refetchInterval: (query) => {
      const status = query.state.data?.status;
      return status === "queued" || status === "running" ? 2000 : false;
    },
  });
}
```

`refetchInterval` returning `false` on a terminal status is what stops the
poll: there is no interval to leak and no cleanup to get wrong. **Confirm the
predicate signature against the TanStack Query major you pin** — it changed
between v4 and v5 — and pin an exact version rather than a caret range. A
test asserts the poll stops (`06_build_and_ship.md` §5).

Four behaviours the view must get right:

1. **A `200` from `POST /analyses` is a success.** It means the
   duplicate-submit guard matched an in-flight run; take `analysis_id` from
   the body exactly as from a `202`. Rendering it as an error would make a
   double-clicked button look broken while working correctly.
2. **`503 no_api_key` arrives before anything is queued**, so the submit
   never happened — render the banner and leave the empty state intact.
3. **`status: "failed"` carries the runner's `error` string.** Render it
   verbatim. A generic message throws away the only information on screen.
4. **On terminal status, invalidate `documents`** so the library chip
   updates without a reload.

**Re-run** is the same mutation with an `Idempotency-Key`, which is what
makes the API queue a second job rather than returning the first.

## 5. The chat stream

**`EventSource` cannot be used.** It is GET-only and cannot set headers;
`/chat` is a POST carrying a JSON body. The client is `fetch` plus a
`ReadableStream` reader and about forty lines of framing in `api/sse.ts`.

```ts
const res = await fetch(`${BASE}/chat`, { method: "POST", headers, body, signal });
if (!res.ok) throw await toApiError(res);     // 503 arrives here, before the body
const reader = res.body!.pipeThrough(new TextDecoderStream()).getReader();
// accumulate into a buffer; split on "\n\n"; parse "event:" and "data:" lines
```

Events, per `05_api_plan.md`: `text` (append a delta), `tool_call` (update
the working line), `citations` (once), `done` (usage, cost, model),
`error` (terminate cleanly, keep what arrived).

Three things `EventSource` would have given for free and must now be written:

1. **Reconnection.** There is none. A dropped stream is a failed turn: keep
   the partial text, mark the turn incomplete, offer a retry. **Never leave a
   bare spinner** — the one failure mode a live demo cannot survive.
2. **Cancellation.** An `AbortController` per turn, aborted on unmount and on
   a new question, or a backgrounded stream keeps appending into a component
   that is gone.
3. **Buffer discipline.** SSE frames split across chunk boundaries. Parse
   from an accumulating buffer, never per chunk. This is the single most
   likely source of a subtle bug in the front end, which is why `sse.ts` is
   pure, separate from React, and tested against split-mid-frame fixtures.

`sse.ts` exposes an async generator of typed events and knows nothing about
React. The view consumes it, appends deltas, and renders the citations once
the `citations` event lands.

## 6. Error rendering

`api/errors.ts` is a total map from `code` to a surface and its copy —
`01_ui_spec.md` §4 is its specification. It exports one function:

```ts
function surfaceFor(error: ApiError): ErrorSurface
```

`ErrorSurface` names *where* (inline-at-control, replaces-card, blocking
banner, full-pane) and *what* (title, body, whether there is a retry). The
views switch on the surface, not on the code, so a new code needs one table
row and no view changes.

Three rules, enforced here rather than remembered:

1. **`hint` is always the second line.** It is written for a person
   (`05_api_deltas.md` §4); render it as prose, not as a code.
2. **An error never destroys work.** A failed question keeps its text in the
   input. A failed analysis keeps the previous report on screen.
3. **Unknown codes fall back**, they do not throw. The API may grow a code
   before the UI knows about it, and a generic inline error is a better
   outcome than a white screen.

## 7. What the UI computes, and why that is allowed

The no-logic rule (`02_architecture.md` §4) has exactly three documented
exceptions, all presentational:

| Value | From | Why the UI |
|---|---|---|
| The **Overall** tile | worst of `results[].compliance_state` | A presentation decision about severity ordering, not a backend fact |
| **Quotes verified** `n / m` | counting `relevant_quotes[].verified` | Two counts over data already on screen |
| The library's **last analysis** wording | `last_analysis.states` counts | The API returns counts precisely so each client picks its own words |

If `totals` ever grows these, prefer them and delete the computation. Nothing
else in the UI derives a fact about a contract.
